### Why the plan should change
- **"The money never left" is justified, and it can be proved.** All 16 returning deposits have the ID `RETURN-<withdrawal id>`, with the exact opposite amount, at most 4 days later. None has a bank row. So no 7-day guess is needed.
- **The plan matched real data, partly by luck.** It dropped the same 32 rows as the ID rule and differed on 0 days. On 24 Aug, Scalable's -€400 had two possible matches the next day: the real Commerzbank +€400 and an unrelated Revolut +€400. Only the shared date saved it.

  - 9 Aug: €300

- **It only fixes days before 7 Nov.** The same errors will return on real synced days from now on.
- **Re-running on new statements is the wrong answer.** One run took 85 Scalable calls. Older prices also get thinner as they age (daily, then every 2 days, then monthly), so a late re-run would lose detail.

### Better design
1. **Drop returned withdrawals in the history job,** by exact ID only. If Scalable changes its ID format, a dip reappears, but no real money gets erased.
2. **Save Scalable's real transfers in their own rows,** and add new ones at each sync.
3. **Add one pure "money in transit" step in `netWorthSeries`.** For each own transfer with two dated sides, keep net worth flat between the dates.
   - Pairs come from linked `transfer_id` rows.
   - Scalable rows match only bank rows with `kind='transfer'` that carry Scalable's IBAN or "Scalable Capital Broker" wording, within 3 days. The IBAN is already in `own_account_identifiers`.
