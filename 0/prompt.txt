## Design decisions
- **Owner precedence uses two triggers on `correction_events` instead of edits to each owner RPC.**
  - Before an owner event is inserted, if it changes category or merchant, the trigger saves the old provenance into `before`, marks the row `'owner'` and sets `owner_touched` on the category or merchant.
  - When an event is marked undone, the second trigger puts that provenance back.
  - So every owner path is covered without rewriting the long `undo_transaction_correction`. Tag-only and note-only edits don't change provenance.
- **`apply_ai_organization` only fills empty labels.** It never overwrites an existing category or merchant.
- **Rule-based and history-based proposals are also stored as `organized_by='ai'`**, not `'rule'` or `'memory'`. The proposal payload doesn't record the basis reliably; all the brief asked for was AI provenance.
- **The reset function is kept** (no grants) so the SQL regression can call it. Running it a second time does nothing.

## Deviations from the brief
- **Undo checks that the row still holds that op's labels, not the version.** Importing a row also bumps its version, which would have blocked Undo. The test covers this case.
- **`apply_ai_organization` takes an extra optional `p_proposal`** and `organizer_ops` has a `proposal_id` column. Crash recovery and the Undo button need to know which ops came from which proposal.
- **Categorize payloads carry an optional `identityKey`.** `ruleKey` is null for keys shorter than 3 characters, so suppression would otherwise miss them.
- **Rules in the reset:** a rule counts as "unchanged" when its version, merchant, category and enabled flag still match `saved_rule_after`. Rules this reset already restored are compared by those fields alone, so chains of auto-applied reviews unwind newest first. Before deleting a rule, `organization_reviews.saved_rule_id` is set to null; the review's before/after copies are kept.
- **Merchants in the reset:** a merchant counts as created by an auto-apply review if its name matches the review's `merchant_name` and it was created no earlier than the review. Auto-apply did both in one transaction, so the times match. Unused ones are deleted; used ones are marked `created_by='ai'`.
- **The reset marks each auto-apply batch as undone** even when some events were kept. That lets the owner undo the leftover rows one at a time; otherwise the organization review page would block it.
- **Old test files touched:** `import-organization*.sql` now ignore the new provenance columns in their "financial truth" comparisons. `reset-workspace.sql` and `workspace-isolation.sql` got `organizer_ops` fixtures, and the isolation test also tries `undo_ai_organization` on another workspace's op.

## Decisions
- **Exchange modelling:** `transactions.kind` only allows `ordinary`, `transfer` and `refund`, so an exchange is a transfer with a marker. The new `mark_own_exchange` marks each leg on its own and records `rule: 'exchange'` and `exchange_with: &lt;other leg&gt;` in the correction event, so the existing `undo_own_account_transfer` takes it back leg by leg.
  - Legs in two currencies aren't linked with `transfer_id`, because `link_transactions` needs a dated FX rate. Writing the bank's rate into `fx_rates` would change net-worth conversion and amount to inventing a rate.
  - The transaction drawer now says "Currency exchange…" and links the other leg.
- **Identity link storage:** a nullable `transactions.identity_id` column. Setting it doesn't bump the version, and no guard or recurring check looks at it. Rows keep their first identity, so reruns change nothing; splitting identities comes later.
- **Memory apply:**
  - **Which rows:** "blank" means the row has no category and no recorded organizer. Rows the import gave a merchant still count as blank.
  - **The batch:** one batch with `operation: 'metadata'` events, undone through `undo_transaction_batch`. Rows are then marked `organized_by='memory'`, and the AI can't overwrite them afterwards.
  - **What undo keeps:** undoing the batch leaves the memory record itself in place.
  - **Processors:** a processor without its description is refused.
- **Pair cards:** these reuse the `own_transfer` kind and card, with a payload of `{transactionId, pairWith}` and a key of `own_transfer:&lt;out&gt;:&lt;in&gt;`. Accepting links the two rows with `link_transactions` as the owner. A declined card is never raised again.
- **Landing:** identity resolution runs inside the existing `linkOwnTransfersStep`, before linking and in its own try/catch. The step keeps its name so imports already running resume cleanly, and a failure never fails an import.
- **Reset:** the new tables cascade from the workspace and point at categories and merchants with set-null, so `reset_workspace` needed no change.

## Deviations and open issues
- **Processor matching:** processors are matched by name, or by description when there's no counterparty name. I didn't hardcode any creditor ids.
- **Person detection** also excludes names containing organization words such as "Stadtwerke" or "Bank"; without that, "Stadtwerke Beispiel" counted as a person. A person's free-text description is never used as an alias.
- **Merchant IBANs:** an IBAN alias can merge merchants that are paid through one processor's shared IBAN. Card rows don't use IBANs, which avoids the common case.
- **Ownership by account id alone:** this proof can pair two legs, but a lone leg can't be marked because there's no RPC for it.
- **Card volume:** cards for unproven pairs have no date limit, so the first run on a long history may raise many.
- **Not done:** I added no new live test that runs `linkOwnTransfers` end to end against the database, no new owner-facing UI for questions or memory (that's PR 6), and no browser tests.

**How it works now**
- **Debounce:** imports and syncs start a run that waits 3 minutes. It then also waits, polling every minute for at most 30 minutes, while any bank sync of the workspace still holds its lease. Everything that lands meanwhile joins that waiting run. A request that arrives while a run is working marks it, and that run starts exactly one follow-up when it finishes. Manual and backlog starts still begin at once.
- **Only analyse what changed:** after organizing, the analysis waves run only if the workspace's transactions changed since the last completed analysis. Manual runs always analyse. I used a fingerprint (row count, sum of versions, latest `created_at`) instead of an `updated_at` column, because many SQL functions compare whole `transactions` rows and a new column there was risky.
- **Leftovers:**
  - The run records when to retry rows it left blank: when the plan limit resets if the provider says so, right away after a spent run budget, otherwise in an hour.
  - Until then later runs don't ask the AI, and the hourly check retries at that time.
  - Rows the AI actually failed on are not retried this way, so they can't loop.
- **Daily sync:** once any account in a workspace is due, its other banks join if their last try was at least 12 hours ago. That costs one extra fetch on the day they line up and stays under the PSD2 limit.
- **First review:** starts after a finished pass once every bank's history has arrived, or 24 hours after the first rows. The hourly backlog cron catches the deadline. It no longer starts from the import or bank-sync workflows.
- **Budget:** still runs only when the owner has spending limits.
