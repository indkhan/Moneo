# E04 — Grounded persistent AI

These are the canonical refinements for E04. `Ready` means specified; implementation still requires every listed dependency to be Done. All fixtures are synthetic. Deterministic provider doubles run in CI; live Muse Spark 1.3/OpenRouter qualification is bounded and separate and never authorizes a production privacy downgrade.

For each story, the orchestrator must add the standard execution record from `STORY-TEMPLATE.md` before changing its status to In progress: assignee/branch/worktree, base and implementation SHAs, exact tests, reviewer/verdict/reviewed SHA, latest-main candidate SHA, merge/post-merge smoke, and remaining blockers. Empty fields are not evidence and no worker may self-approve or merge main.

## E04-S01 — Enforce provider policy and atomic usage budgets

Status: Ready | Release: R1 | Epic: E04 | Dependencies: E03-S08, E02-S04

Outcome: An authorized model dispatch is admitted only after tenant policy, route, concurrency and money/token budgets are atomically reserved; completion reconciles actual or unknown usage without overspend.
Contracts: Product §§4, 29–30; architecture §§124–138, 175–190, 416–489; existing `ai_policies`, exclusions, permits, durable jobs and OpenRouter mapping transport.
Scope: Extend the existing policy/permit path with one shared server dispatch function, explicit development and production routes, bounded input/output, timeout/retry classification, atomic PostgreSQL reservation, reconciliation and revocation recheck. Expected ownership: `apps/web/src/ai-*`, worker dispatch, additive migration, focused real-PG tests. No provider registry.
Out of scope: Chat persistence, tools, UI, custom keys/models/prompts, production route qualification.
Acceptance:
1. With a synthetic €10/token/concurrency budget, a barrier-started race admits only reservations within every limit; rejected calls never reach transport.
2. Success reconciles measured usage; missing/invalid provider usage remains `PENDING` with the full reservation held; terminal failure releases only under the documented class.
3. Policy/exclusion/version revocation after enqueue but before dispatch fails closed; production never falls back to a training-permitted route.
4. Timeout and retry are bounded (one retry only before any provider output, 30 s/request, configured output cap); idempotent replay cannot double-charge or double-dispatch.
Invariants: Tenant/policy at enqueue and dispatch; decimal-string cost units; credentials stay server-side; unknown is not zero; permits fenced by attempt and policy version.
Failure lifecycle: Durable job owns retry; ambiguous dispatch remains charged/reserved pending reconciliation; cancellation prevents later dispatch but accounts for accepted provider work.
UI/accessibility: Not applicable — shared dispatch layer; errors are typed for later UI.
Data changes: Add immutable usage/reservation ledger fields only as needed; forward additive migration, code-first rollback, never erase unresolved usage.
Observability: IDs, route class, token counts, reserved/reconciled cost, latency and error class; no prompts, outputs, keys or finance payloads.
Limits: 5 concurrent calls/workspace default, 30 s/provider attempt, 2 attempts only when safe, 64 KiB request and configured output-token ceiling; tests declare exact budget values.
Verification: `npm run test:ai-dispatch` (real PG race/replay/revocation/unknown usage), existing `test:policy`, `test:jobs`, `test:job-recovery`, typecheck and worker/web builds; optional bounded live synthetic probe reported separately.
Review focus: check-then-act budget races, release-on-unknown, stale policy, retry after output, secret/payload logs, production fallback.
Rollout/rollback: Pre-release flag; disable new dispatch first, retain usage ledger and accepted jobs.

## E04-S02 — Persist chat and its worker-owned model loop

Status: Ready | Release: R1 | Epic: E04 | Dependencies: E04-S01, E02-S02

Outcome: Users create persistent threads and turns; one durable worker owns generation, and reconnect resumes authoritative saved activity without duplicate effects.
Contracts: Product §4; architecture §§139–174, 175–226; E02 durable job/fencing and E04-S01 dispatch.
Scope: Thread, turn, generation-attempt and activity rows; tenant-scoped HTTP create/list/read/send; worker loop with one active fenced attempt; resumable event cursor. Persist complete model chunks or one final message—never concatenate independent attempts.
Out of scope: Tools, contextual panel, writes, branching conversations, realtime voice.
Acceptance:
1. Send returns an accepted durable turn/job; reconnect from a cursor yields ordered saved activity and the final turn.
2. Worker death before/after dispatch produces at most one published assistant turn; ambiguous output is marked interrupted and retry starts a visibly separate attempt.
3. Same-key replay converges; tenant-swapped thread/turn/cursor IDs are uniformly not found; RLS denies unscoped reads.
4. Cancelled/failed/provider-unavailable states remain inspectable and retryable within E04-S01 accounting rules.
Invariants: Append-only turns/activity, attempt fencing, tenant composite keys, server-owned role fields, no raw provider transcript logs.
Failure lifecycle: Lease/recovery follows E02; partial output is stored as non-authoritative attempt activity and never silently promoted after cancellation.
UI/accessibility: API only here; later UI receives explicit queued/running/interrupted/failed/completed states.
Data changes: Additive chat tables with FORCE RLS, composite tenant FKs and cursor index; rollback disables writes and retains conversations.
Observability: Thread/turn/job/attempt IDs, state transitions, counts and latency only.
Limits: 200 turns/thread, 32 KiB user turn, 100 activity events/page, one active generation/thread.
Verification: `test:chat` with real PG/Redis recovery, replay, fencing, reconnect and tenant probes; regress dispatch/jobs/recovery/typecheck/builds.
Review focus: duplicate publication, mixed attempts, cursor oracle, role forgery, cancellation race, unbounded history.
Rollout/rollback: Pre-release flag; stop consumers before code rollback; retain rows.

## E04-S03 — Expose scoped tools, evidence and dispatch revalidation

Status: Ready | Release: R1 | Epic: E04 | Dependencies: E04-S02, E03-S04

Outcome: The worker can call a small allowlisted set of server tools backed by authoritative shared queries and frozen evidence, never SQL or model-selected capabilities.
Contracts: Product §§2.3, 23; architecture §§124–174, 416–489, 535–538; completed E03 server-owned calculation/evidence boundary.
Scope: Tool schemas/adapters for transaction search/evidence, account/balance reads and authoritative financial totals; per-run capability/context object; strict arguments/results caps; evidence references; policy recheck before each tool and publication.
Out of scope: Arbitrary SQL, network/browser tools, writes, artifact SDK, projections.
Acceptance:
1. Valid calls return bounded decimal-string results plus coverage/version/evidence IDs identical to UI/shared queries.
2. Malformed/oversized/unknown tool calls fail typed without execution; prompt text cannot add a tool, tenant, account or excluded object.
3. Policy/exclusion/data-revision changes block stale tool dispatch/publication while already-dispatched cost remains honestly accounted.
4. Unsupported questions return unavailable/abstention rather than model arithmetic or fabricated totals.
Invariants: Models receive schemas, never SQL/credentials; authorization and exclusions apply before aggregation; evidence is server-computed and immutable.
Failure lifecycle: Tool effects are read-only/idempotent; timeout/cancel halts future calls; corrupted results fail the run safely.
UI/accessibility: Evidence references have stable labels for S04 navigation.
Data changes: Reuse calculation/chat evidence; additive linkage table only if immutable IDs cannot be represented in existing activity.
Observability: Tool name, bounded counts, evidence/version IDs and timing; no arguments/results containing finance data.
Limits: 8 tool calls/run, 100 rows/tool, 64 KiB tool result, 10 s/tool.
Verification: `test:ai-tools` real PG with tenant swaps, exclusions, revision race, malformed calls and independently expected totals; regress E03 exit/chat/dispatch.
Review focus: capability injection, adapter drift, excluded rows in aggregates, stale publication, evidence not reproducible.
Rollout/rollback: Disable tool capability; chat without tools remains explicit/limited.

## E04-S04 — Deliver contextual chat, activity and Stop

Status: Ready | Release: R1 | Epic: E04 | Dependencies: E04-S03

Outcome: A persistent keyboard-accessible AI panel shows explicit context, saved activity/evidence and reliable Stop/retry across reloads.
Contracts: Product §4 and accessibility baseline; architecture frontend/security sections; E04-S02/S03 APIs.
Scope: Server-rendered panel plus minimal client behavior; thread list, turns, context chips, activity, evidence links, Stop/retry, loading/empty/error/reconnect states; sanitized markdown subset with no remote resource fetching.
Out of scope: Rich editor, voice, external previews, artifacts, mobile-native app.
Acceptance:
1. From account/transaction/workspace pages, removable context is displayed before send and revalidated server-side.
2. Reload/reconnect restores turns, terminal activity and evidence; Stop prevents future tools/publication within the documented in-flight bound.
3. Malicious markdown/links/images cannot execute script, navigate automatically, fetch remote resources or access host data.
4. Keyboard-only use, focus transitions, status announcements, 320 px layout and error recovery pass the critical browser journey.
Invariants: Context IDs are hints, not authority; host renders trusted components; no unsafe HTML.
Failure lifecycle: Stop is idempotent; ambiguous provider work remains accounted; retry is a new attempt.
Data changes: None beyond S02/S03.
Observability: UI action/state/error classes only.
Limits: Virtualize or cap rendered history at 200 turns/500 activities; no external preview requests.
Verification: `test:chat-ui` plus Playwright critical journey, hostile markdown and reconnect/Stop; regress UI/web build.
Review focus: XSS/exfiltration, hidden context, misleading Stop, lost activity, keyboard/focus regressions.
Rollout/rollback: Hide panel flag; APIs/data retained.

## E04-S05 — Confirm financial actions in trusted host UI

Status: Ready | Release: R1 | Epic: E04 | Dependencies: E04-S04

Outcome: Chat may propose exactly one R1 write—create a manual transaction—but only the trusted host can confirm a payload-bound, expiring, versioned action through the existing command path.
Contracts: Product §15; architecture command/consent/security contracts; existing `transactions.createManual` idempotency/audit/undo.
Scope: Read-only proposal tool, server proposal record/hash, host confirmation component, expiry/actor/policy/version checks, command execution and audit/undo link.
Out of scope: External money movement, bulk writes, model-issued consent, other action types.
Acceptance:
1. Proposal visibly shows account, amount/currency, direction, date and description; confirm executes the shared command once and exposes audit/undo.
2. Tampered payload, expired/replayed token, wrong actor/tenant, stale account/policy/version and model-authored “confirmed” text fail without writes.
3. Concurrent confirms have one winner; response loss plus retry returns the same operation/result.
Invariants: Confirmation is host UI plus authenticated request, never prompt/tool text; exact money and existing authorization remain authoritative.
Failure lifecycle: Proposal expiry is terminal; command retry follows existing journal; cancellation before confirmation has no effect.
UI/accessibility: Native dialog/form semantics, focus trap/return, explicit consequences, keyboard confirm/cancel, preserved input on conflict.
Data changes: Add bounded proposal table with FORCE RLS and expiry; deletion lifecycle included later.
Observability: Proposal/action/operation IDs and outcome only, never amount/description.
Limits: 15-minute expiry, one action/proposal, 20 open proposals/user.
Verification: `test:ai-action` real PG races/replay/tamper/tenant/version/audit/undo plus browser confirmation journey.
Review focus: consent forgery, confused deputy, stale payload, duplicate effect, amount leakage.
Rollout/rollback: Disable proposal capability; retain audit and accepted transaction.

## E04-S07 — Qualify grounded AI behavior and close E04

Status: Ready | Release: R1 | Epic: E04 | Dependencies: E04-S06

Outcome: A versioned synthetic evaluation and integrated journey demonstrate grounded chat, tools, evidence, exclusions, Stop and confirmed action; deterministic CI and live Muse Spark 1.3 results are reported separately.
Contracts: Product evidence-first AI; architecture eval/provider/privacy gates; all E04 stories.
Scope: Freeze rubric/dataset before execution; deterministic protocol suite; bounded live candidate run using synthetic data; integrated browser/system exit; defects only, no new product scope.
Out of scope: Production qualification (E08-S03), real customer data, benchmark shopping, artifact generation.
Acceptance:
1. Predeclared dataset has at least 40 cases: 12 numerical grounding, 8 evidence completeness, 6 abstention/missing coverage, 6 exclusions/tenant/hostile input, 4 tool selection and 4 action-consent cases.
2. Deterministic protocol/security cases pass 100%; live Muse Spark 1.3 achieves ≥90% overall, 100% unauthorized-action refusal, 100% exact claims delegated to authoritative tools, and zero unsupported full-coverage claims.
3. Integrated send→tool→evidence→reconnect→Stop/retry→proposal→trusted confirm journey passes with exact ledger usage and no duplicate effects.
4. A live outage/rate limit is reported as unavailable, never converted into a pass or privacy fallback.
Invariants: Expected numbers/evidence are independently calculated; model output never becomes authoritative arithmetic or consent.
Failure lifecycle: Freeze run ID/model/route/prompt/tool versions; failed threshold blocks E04 exit and records cases for correction without tuning the hidden expected outputs.
UI/accessibility: Critical browser journey includes keyboard, focus, loading/error and 320 px checks.
Data changes: Versioned synthetic eval fixtures/results contain no secrets or personal data.
Observability: Aggregate scores, case IDs, latency/tokens/cost and error class; redact prompts/financial payloads from normal logs.
Limits: ≤40 live calls, ≤US$5 configured reservation, ≤20 minutes, temperature/config pinned when supported.
Verification: `test:ai-eval`, all E04 suites, E03 exit, full deterministic matrix, builds, deliberate-failure gate, staging smoke, diff/secret checks; `probe:ai-e04:muse-spark-1.3` is manual/bounded and separate.
Review focus: self-derived oracles, threshold changes after results, hidden unauthorized actions, mock/live conflation, stale reviewed SHA.
Rollout/rollback: E04 remains pre-release if thresholds fail; no production traffic authorization.
